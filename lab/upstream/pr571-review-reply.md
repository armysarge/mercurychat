Thanks for the careful read. Both are in `940b946`.

**1. Unkey not paced.** `hamlib_reopen()` takes a `paced` flag. Key-ups pass `true`; a PTT OFF passes `false`, as you sketched. One correction to the CI reading: in the DATAC3 test, the `PTT OFF not sent` line comes from the OFF's *own* failed reopen. A DATAC3 frame is about 3.9 s on air, longer than the 3 s pace, so that OFF was never suppressed. The case you describe does happen with frames shorter than 3 s, so there is now a second test, `TestHamlibPttOffIsNotPaced`, which uses DATAC0 (about 1.1 s on air). Before the change it logs one failed reopen (the key-up's) and the unkey is dropped; after, the unkey makes its own attempt.

**2. Lost OFF retried.** `g_hamlib_off_pending` is set when an OFF is not delivered and cleared when any PTT change reaches the rig. While it is set, the OFF is retried every 5 s with the paced reopen, under `g_radio_mutex` via `trylock`, and never while keyed. I did not hang it on the frequency poll alone: that runs from the UI status publisher, which only exists with `-G`, so a headless Mercury would never retry. The retry is now in a new `radio_io_service()`, which `main()`'s 500 ms idle loop calls. The frequency poll calls it too, which covers hosts that drive the engine without `main()`, and it brings the frequency readout back after a rigctld restart, as you noted. `radio_host.c` gets a no-op. In the restart test, step 3 now starts rigctld and sends nothing: the rig is released 5.3 s after the lost OFF.

Results: both tests fail on `5e5d7ad` and pass on `940b946`. `TestMercuryTxTest*` (shutdown and forced-exit unkey) are 3/3 before and after, and `test_radio_io_frequency`, `test_radio_port` and `test_host` pass. I've updated the description to match.
